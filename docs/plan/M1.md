# M1 — Alpha source-map data module (src/alpha-maps.ts)

> **Base fact**: this repository is a faithful TypeScript port of
> [GeminiWatermarkTool](https://github.com/allenk/GeminiWatermarkTool) —
> a C++ tool that removes Gemini's visible image watermark via
> deterministic reverse alpha blending. The C++ source (v0.3.2, commit
> `7c6a99f`, checked out at `$GWT_UPSTREAM_DIR`) is the sole behavioral
> authority; we reproduce its behavior, quirks included, never "improve" it.
>
> **Required upstream reading (in full, before writing code)**:
> `src/core/blend_modes.cpp` — `calculate_alpha_map`;
> `src/core/watermark_engine.cpp` — the constructors,
> `init_alpha_maps` / `init_alpha_maps_v2`, and `get_alpha_map(size,
> variant)`; the array declarations/comments in
> `assets/embedded_assets.hpp` (skip the hex payload).

Prerequisite: M0 complete (kit regenerable, `test/data/cases` in place).

## Context

The whole engine rests on four calibrated **alpha maps** — the watermark's
per-pixel opacity, recovered by upstream from captures of the watermark on
pure black (`α = max(R,G,B)/255`). The C++ tool embeds them as PNGs; a
zero-dependency npm package cannot decode PNG at runtime, so this
milestone bakes the decoded bytes into a TS module generated at build
time.

Consumers: blend (M2) uses the maps directly for canonical sizes;
`effectiveAlphaMap` (M3) derives every other logo size from the 96px
sources; detection (M4) uses them as matching templates. Getting the data
byte-identical to the kit's extraction is the entire point — a single
transposed pixel would silently skew every downstream equivalence test.

**Scope**: expose only the four **source** calibration maps
(V1-48 / V1-96 / V2-36 / V2-96). Derived sizes (V2-48, the 42px class)
are entirely out of this milestone — `effectiveAlphaMap` belongs to M3.

## Commit 1 — generator + data module

1. `tools/gen_alpha_module.py`: read
   `$GWT_REFERENCE_DIR/alpha/{bg_48,bg_96,bg_b_36,bg_b_96}.png`, take
   per-pixel `max(R,G,B)` as uint8 arrays, base64-encode, and render
   `src/alpha-maps.ts` (template embedded in the script; file header gets
   a provenance comment + the generation command). Also print each map's
   `sha256(uint8 bytes)` and 4 checkpoint tuples `(x, y, value)` — pick
   asymmetric coordinates (e.g. (5,9), (9,5), (w-3,2), (2,h-3)).
2. `src/alpha-maps.ts` structure:
   ```ts
   const B64: Record<string, {w: number, h: number, data: string}> // 4 entries
   function decodeBase64(s: string): Uint8Array   // own lookup-table impl; atob/Buffer forbidden
   const cache = new Map<string, Uint8Array>()    // private, stores uint8
   export function getSourceAlphaMap(
     variant: WatermarkVariant, size: WatermarkSize): Float32Array
   // returns a fresh Float32Array (uint8/255) per call; never expose the cache
   ```
   Corresponds to C++ `WatermarkEngine::get_alpha_map(size, variant)` +
   `calculate_alpha_map` (blend_modes.cpp).
3. Export `getSourceAlphaMap` from `src/index.ts`.

## Commit 2 — tests

`test/alpha-maps.test.ts` (CI self-contained; expected values are printed
by the generator and hardcoded):

- Dimension assertions: 48²/96²/36²/96²
- Per-map uint8 SHA-256 (via node:crypto — Node APIs are fine in tests)
- 4 checkpoint values per map, exact
- Mutation isolation: after `getSourceAlphaMap(...)[0] = 999`, a fresh call
  returns unchanged data
- base64 decoder unit tests: empty string, several RFC 4648 vectors
